# TET-43: a renderer change is not a hand edit

Written against tetel at b490574. Any change to what `render` emits makes a committed memo fail `check` with `[provenance-drift]`, and the message blames the memo. This memo keeps the failure, makes its diagnosis exact, and adds a remedy that cannot overwrite a hand edit.

*cites: C1, C3, C10, C11*

## The defect

Provenance is one byte comparison: the snapshot beside the memo is rendered by the current build, and anything other than exact equality is drift. Three things feed that comparison: the document, the snapshot, and the renderer. The outcome does not say which of them moved.

*cites: C2*

The ticket's observation still reproduces. A build that differs from the pin only by one line appended to the rendered output fails both memos the test suite pins, and tells the reader to look for a hand edit that does not exist. That test runs in CI, so today a renderer change has to re-render at least those two memos in the same commit, or CI stays red.

*cites: C3, C4*

## What the ticket's directions run into

Grading only what the author wrote (option 2) looks like it removes the class, but the sections render generates are not decoration. `check` reads the claims it grades out of the rendered ledger. The digests every grading record is keyed to were computed over the propositions read from it. The target rows and transplant ids are parsed back and re-verified. Excluding these sections from provenance would let a hand edit change what gets graded, with nothing reporting it.

*cites: C5*

The ticket's reasons for not simply re-rendering are half right. The workspace is not needed: the snapshot is itself enough to render from, which is how `check` already works, and all 12 committed memos reproduce exactly from theirs. The current message's "re-render" points at workspaces that live only on the authoring machine. The digest risk, on the other hand, is real. A change to how a claim is written into the ledger, one that survives the importer's trimming and unescaping, changes that claim's digest. So re-rendering can silently put graded claims out of proof.

*cites: C6, C7*

A hand-bumped render-format id (option 1 as written) moves the problem rather than solving it. It is correct only while every editor of `render` remembers to bump it, and the build label cannot stand in for it, since that changes on every build.

*cites: C14*

## The design

**A render record.** `render --out` writes `render.json` into the snapshot: the document's digest, one digest per shipped snapshot file, and the build label. `snapshot::write` takes over the whole publication from both callers, in this order:
1. Remove any existing record.
2. Write the document.
3. Make the snapshot a mirror of the workspace, deleting files the workspace no longer has instead of carrying them forward.
4. Write the new record, only if a render of that snapshot reproduces the document exactly.

An interruption anywhere leaves no record. That is never a false accusation of an edit: at worst it is `Unattributed`, and if nothing had changed yet, an unrecorded match. A carried-forward file can no longer make a correct render fail its own certification. Rendering and copying read the workspace separately, so the final check is what lets the record certify the pair.

*cites: C8*

**An attributed diagnosis.** When the re-render differs, the record says which input moved:
- the snapshot (`SnapshotEdited`), including a recorded file that has gone missing, which would otherwise pass for a renderer change because rendering without the file succeeds;
- the document (`DocumentEdited`);
- neither, which leaves the renderer (`RendererChanged`, naming the build that rendered it).

A memo with no record is `Unattributed`, and its message names the renderer among the possible causes. Digests are kept per file because the list of snapshot files grows, and a single digest would misread every existing snapshot the first time it did.

A build from before this change writes no record and deletes none. So it can leave a matching pair beside a record of a different document, or, when the rewrite changes nothing render reflects (`refusals.log`, `acks.jsonl`, a fact field it never prints), beside a record that disagrees on those files alone. `check` reports either as `StaleRecord` as soon as it happens, while the renderer has not moved. Waiting would mean it surfaced at the next renderer change as an edit that `rerender` refuses. Only if a record-less render and a renderer change both land before any check is the case read as an edit. For that, the `DocumentEdited` and `SnapshotEdited` messages name both causes.

*cites: C9*

**The failure stays a failure.** `RendererChanged` is still a machine failure, under its own row kind. So is `StaleRecord`, so that it is fixed while the author still has the context. The current build parses the ledger, the target rows and the transplant ids out of the document in the layout it would render today. It cannot vouch for its own verdicts on a document in an older layout. The remaining cost is deliberate: a renderer change still reddens the committed-memo test until the memos are migrated in the same change. That is now one command, not an investigation.

*cites: C10*

**`tetel rerender`.** A CLI command renders a memo from its own snapshot, and every record it writes is for a document it has just made equal to that render.
- It migrates a `RendererChanged` memo and replaces a stale record. It seals an unrecorded memo that already matches, and leaves a sealed, clean one byte-for-byte alone.
- It will not reseal over a record that agrees on the document but not on some snapshot file unless the operator vouches, with `--reseal`, that a record-less build changed them. An edit that render does not reflect still renders to the same document: `identity.json`, `acks.jsonl`, or a fact's captured output. Digests cannot tell it from such a build, and resealing would erase the only trace of it. The flag is separate from `--unattributed`, so vouching for one state never consents to the other across a glob.
- It refuses a memo whose document or snapshot differs from its record.
- It refuses an unrecorded memo unless the operator vouches for the migration with `--unattributed`, and even then it writes the render, never the bytes as they stand.
- It refuses any memo where re-rendering would change the set of ledger claims or a claim's proposition, and names the claims, because that would put their grading out of proof. A document whose ledger this build cannot read at all is refused as unreadable, not as every claim having changed.

It is not an MCP tool.

*cites: C11*

**Backfill, then A10.** The implementing change runs `tetel rerender` over every memo that has a snapshot at that time: the 12 committed at the pin, plus any committed since, this one among them. Each is expected to match already, so each only gains a record. One that does not is a finding, not something to force.

This has to land before TET-83 changes render output; otherwise those memos would be `Unattributed` at the moment they first need migrating. A memo that a pre-record build rewrites in between is reported as `StaleRecord` and repaired by `rerender`, with `--reseal` where the files moved only in ways render does not reflect. A10 should start by checking every memo.

*cites: C12*

**Line endings pinned.** The implementing change adds a `.gitattributes` marking `docs/design/**` as `-text`. Without it, a clone that converts line endings on checkout would present every memo as a hand-edited snapshot, a confident misattribution where today there is only unattributed drift.

*cites: C16*

## Other readers of the re-render

Two other readers assume the document is in the current layout.

The first is the line numbers printed beside prose revised after proof, which come from rendering the snapshot. They are printed as document lines only when provenance matches; otherwise the entry says the line is unknown and why.

The second is the document-side halves of the target census and premise checks. They parse rows out of the document and call any row the snapshot lacks "not written by `tetel target`". Under `RendererChanged` the record vouches that document and snapshot were rendered together, so those rows are the tool's own. There, both halves are skipped with a note, rather than repeating the misattribution this memo removes. Under every other outcome they run as they do today, because an edited document is exactly what they exist to catch.

*cites: C13*

## Falsifying tests

Eighteen tests pin the decisions above, each with the mutation that must turn it red:
- Classification: all five outcomes, each one failing, plus a missing recorded file and growth of the file list.
- Publication: the record removed first, written only on a reproducing render, and the snapshot mirrored.
- `rerender`: every branch, including the refusal to reseal over an edit that render does not reflect.
- The two readers gated on provenance.

The backfill and the `.gitattributes` are pinned by their own diffs, not by tests.

*cites: C15*

## Out of scope

The record guards against accidents, not adversaries. Anyone who can edit the snapshot and re-render could already forge provenance. Editing `render.json` now also forges an attribution, which is no stronger than that.

The ticket's second finding, a memo rendered by a stale MCP server, is not detected as staleness by this design, since such a memo matches under the build that wrote it. A stale server built after this change writes its own build label into the record, which makes it visible after the fact. One built before it leaves a stale record, which `check` reports. Detecting the stale server itself stays with TET-31.

When the re-render matches, `check` compares the per-file digests as well as the document's. A record-less rewrite can change the snapshot only in ways render does not reflect, and a check that passed it would leave the record to fail at the next renderer change. So a hand edit to `identity.json` or `acks.jsonl` in a sealed snapshot is now reported too, as a stale record, and only the operator can say which of the two it was. A bulk `--all` form of rerender is deferred, since a shell glob covers it.
