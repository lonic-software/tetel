# TET-46 — a `look` must not return tetel's own output

This memo was written against a single tree: commit b57bf8edb4c1eb59d8d86a8327179f43a9cb0829, "design: anchor the residue at first proof, not at the last pass", with no tracked source file differing from it. The reader who wants to re-take an observation should check that pin out first. Which tree each individual observation was actually taken against is not something this memo asserts — every observation carries its own working-tree marker, and `check` prints those states.

*cites: C1*

The problem in one line: this repository now contains enough of tetel's own output that a `look --grep` rooted at its worktree is mostly a search of previous memos. A census of `NON_COVERAGE` matches fifteen files, fourteen of which are rendered memos, evidence ledgers and snapshot logs, and one of which is the source file that defines the symbol. What follows decides what to do about that, in what order the questions actually forced themselves, and it departs from the ticket in several places — most of them because a clause the ticket asserted about grep turned out not to hold when run.

*cites: C7*

## The rule

The change lands in one function, `look_grep`, and it is a decision about whether to pass exclusion flags at all rather than a decision about which flags to pass. `look_grep` already distinguishes the two cases the rule needs: it adds `-r` only when the root is a directory, and it hands the root string to grep exactly as the caller spelled it. So — when the root is not a directory, the caller has named one file, and no exclusion is passed. When the root is a directory with a path component ending in `.tetel`, the caller has named inside tetel's own output, and no exclusion is passed. That one component test is the entire root predicate, and the reason is worth stating because the obvious design has three: the other two artifacts, an evidence ledger and a rendered memo, are files, so a root naming either has already taken the not-a-directory branch and never reaches a content test. Only for a directory root with no `.tetel` component are the exclusions passed: `--exclude-dir=*.tetel`, `--exclude=*.evidence.jsonl`, and one `--exclude` per rendered memo, each spelled path-prefixed in the same spelling the root was given in. Both of the withholding branches are forced rather than chosen, and the next section is why.

*cites: C11*

## What the greps on this machine actually do

The ticket asserts that the implementation is small because `look_grep` already shells out to `grep -r -I -n -H` and both greps CI runs support `--exclude-dir` and `--exclude`. Half of that is right and can be shown here. The binary `Command::new("grep")` resolves to on this machine is /usr/bin/grep, BSD grep 2.6.0-FreeBSD, with no GNU grep shadowing it under that name; it accepts both flags alongside the flag set `look_grep` already passes; `--exclude-dir='*.tetel'` prunes snapshot directories at any depth and `--exclude='*.evidence.jsonl'` drops evidence ledgers. The other half cannot be shown here at all. Nothing in this memo was executed against GNU grep or on Linux, so the ticket's clause about the Linux grep is not verified by this design, and no claim in it asserts anything about that grep. That is a bound, stated, not an omission.

*cites: C2*

The clause that is wrong is the one the ticket did not think it was making. The ticket's first constraint — an explicitly named path must still be read, only traversal skips, "the rule `git` and `rg` apply to ignored files" — is stated as though grep already obeyed it. It does not. A file named explicitly on grep's command line is skipped when `--exclude` matches it, and a directory named explicitly as the recursion root is skipped when `--exclude-dir` matches it; in both cases the identical command without the flag finds the match, so the flag is what removed it. Exactly one of the three arrangements behaves the way the constraint describes, and it is the one nobody would have doubted: `--exclude-dir` does not suppress a file that is named explicitly and searched non-recursively from inside an excluded directory. So the explicit-path exception is not something this design can obtain by choosing flags. It has to be implemented in tetel, above grep, by deciding when to pass the flags at all.

*cites: C3*

The rendered-memo test has a second problem, and it is in the ticket's one-line implementation sketch rather than in its principle. The sketch says: glob for `*.tetel` directories under the search root, strip the suffix, pass the result as `--exclude`. Both halves of that fail. A `--exclude` pattern is matched against the name grep constructs for the file from the root it was given, so with a relative root an absolute-path pattern excludes nothing whatsoever and the search silently returns everything, while the same file spelled relative to the root is excluded correctly. And a suffix-stripped bare basename is not a name — it is a glob that matches that basename anywhere in the tree, which in the measurement removed both a real rendered memo and an unrelated file of the same name that has no snapshot beside it and so is not a memo at all. A wrong exclusion of that second kind is the worst failure available here, because it hides source from a census under the banner of hiding tetel's own output. The pattern must be emitted path-prefixed, in whatever spelling the root itself was given in.

*cites: C4*

## Where the skip is disclosed

The disclosure goes in the whole-search record's label, and it costs nothing in schema. TET-28 already added exactly one record per `look --grep` whose job is to say where a search started rather than what it hit — a `Search` entry when the grep matched, a `NoMatch` entry when it did not, and never both. That record is the natural and the only correct home for a statement about what the search did not visit, because the exclusion is a property of the search and not of any file it found. Putting the text there buys two carriers already built: the memo's Facts table renders each extent entry's label and renders nothing else from it, so the exclusion set is on the page for a reader who has only the committed document; and the pin hashes the label, so two searches with different exclusion sets fingerprint differently even when the text they matched is identical. It should also be printed in what `look` returns, for the author reading it in the moment — but the printed string is the convenience and the label is the record, which is the opposite of the two shapes this project has already been burned by: a warning with no lifecycle, and a refusal trail missing the refusal that mattered.

*cites: C5*

## What it is worth, and what it costs

The ticket's numbers are figures reported inside a memo, which makes them claims that were graded rather than measurements anyone here has made, so the effect was re-measured on this tree directly. A census of the symbol `NON_COVERAGE` over the tetel worktree returns 858,096 bytes from fifteen files. Fourteen of those files are tetel's own output — three rendered memos, three evidence ledgers, eight snapshot logs — and one, `src/report.rs`, is the source anybody grepping for that symbol wanted. With the three exclusions the same census returns 169 bytes from `src/report.rs` alone. Those are bytes grep handed back and bytes a fact would then store; what fraction of them reaches any given caller is a separate quantity, and a later section settles it, because the ticket's answer to it does not survive.

*cites: C7*

Against that, the enumeration the rendered-memo test requires is cheap in the only comparison that matters, which is against the grep it precedes. It is a walk over directories; the grep is a walk over directories that opens and reads every file beneath them. On this worktree — 848 directories against 159,519 files — the enumeration takes 0.130s and one census grep takes 3.953s. So the answer to what happens on an enormous root is that the enumeration is dominated by the search it serves. The answer for an unreadable root is that both stop at the same wall: a directory nobody can open produces the same permission error from each. That is one failure mode, though, and it is the only one measured. Whether the two walks agree on symlinked directories was not tested, and an implementer should not assume it — a difference there would mean the walk misses a snapshot the grep then reads, which is the one way this mechanism fails quietly rather than loudly.

*cites: C6*

## The bug obstructs the memo that fixes it

This design ran into its own subject before it could declare a single modification target, and the shape of that is worth stating rather than working around quietly. TET-28 requires a symbol an implementer is told to modify to be censused by a grep of the whole worktree. Every candidate symbol here was priced first: `look_grep` costs 709,469 bytes, `NON_COVERAGE` 858,096, `censuses` 691,562, `look_path` 688,776, `search_key` 633,291. The interesting number is not any one of them but the floor they share — roughly 0.63 MB is returned whichever symbol is asked for, because it is not about the symbol at all. Dropping snapshot directories and evidence ledgers alone removes between 95.9% and 99.9% of each. So the census requirement is today priced by tetel's own accumulated output rather than by the code being censused: two thirds of a megabyte comes back from grep, and is stored in the fact, per declared target.

*cites: C9*

Then the design paid the price once, deliberately, to declare `look_grep` — and the payment failed in a way that settles the ticket's sharpest question. The search ran and was recorded, but the harness returning results to the author refused to hand back 707,751 characters across 38 lines, and spilled them to a file. So this memo's author never read the output of their own census, while the fact minted anyway and the full 707,751 characters are shipping in the snapshot beside this document. The ticket asked any design to say which path it is changing, the return path or the retention path, and this is the answer from the inside: they are already separable, only the return path currently has a cap, that cap belongs to the harness rather than to tetel, and it fired. The census's own extent is the summary of the problem — ten files matched, eight of them tetel's own output, two of them the source anyone grepping for `look_grep` was looking for.

*cites: C10*

## The figure this design will not carry

The ticket's reframing — the one that moved it to the front of the queue — is that the primary cost is context, quantified as roughly 135k tokens and about 40% of a 336k run. This design does not carry that figure, and the reason is not scepticism but a counter-instance produced in the course of the work. `look_grep`'s return is uncapped in tetel exactly as the ticket says: the grep's whole stdout is copied into what the function hands back, with no length check or truncation anywhere between them. But when this design took a real whole-worktree census, the client refused the 707,751-character result and returned about 1,300 characters of error text naming a spill file. The bytes a census returns and the bytes that enter a model's context are therefore two quantities, and the second does not follow from the first. Anyone wishing to restore the ticket's figure would have to measure the second directly, against a specific client, and say which.

*cites: C12*

What survives is a smaller argument and a better one, and it is the argument this design is built on. The bound that fired was the caller's, not tetel's. tetel returns unbounded output and depends on whoever is holding it to decide that was too much; a different client will not decide anything. That is a defect on its own terms, independent of any token arithmetic — and it is sharpened, not weakened, by how the truncation behaved here. The client disclosed the skip to the author in the moment and left no trace of it anywhere in the fact, so the minted record now carries 707,751 characters of captured output that nobody read, with nothing in the extent saying so. The ticket's own second constraint is that a skip must never be silent. The one skip observed during this design was silent in exactly the way the constraint forbids, and it was not tetel's.

*cites: C12, C10*

## What it does to TET-28's guarantee

The census predicate does not need to know, and should not be taught to. `ExtentEntry::censuses` reads five things — the record's kind, its pattern, that its world root is a real git root, and that the search key equals that root — and reads neither the label nor the output. It was always a predicate about a search's existence and where it started rather than about what the search saw, which is why a symbol with no occurrences is censused by the grep establishing it has none. That property is what lets this change through untouched: a worktree-rooted search is still a worktree-rooted search after it stops walking into snapshot directories. What moves is not the predicate but what a reader may conclude from one, and that is a matter of text in two places — a standing line in `check` saying the policy exists, and the search record's own label saying which exclusions this search was actually given.

*cites: C14*

The standing line is added, not amended, and the ticket is right about why. `check`'s existing entry — "whatever the platform's grep skipped — symlinked directories and binary files bound what a whole-worktree search physically visited" — names two platform accidents and contemplates nothing that tetel chose. Widening it to cover a deliberate exclusion would be the move the ticket warned against, turning "rooted at the worktree" into "rooted at the worktree except what the tool decided to hide" inside a sentence about symlinks. The list's own comment supplies the standard: these lines exist because "a refusal that fired is easily read as coverage it never claimed". A deliberate exclusion is precisely such a case and earns its own line. But it can only ever be the general statement, because every entry in that list is a static string and none is per-search — which is the other half of why the per-search label is not redundant with it.

*cites: C13*

## What to call it, and what not to promise

The maintainer's scope sentence — no `look` should return tetel's own content — should not become the printed guarantee, because after this change it is false. `look_path` refuses a directory, reads exactly the file it was handed, and traverses nothing; it can and should still open a snapshot's `prose.jsonl` for a reader who names it, which is how anyone re-checks a prior memo's record against what it claims. The design leaves it entirely alone. The honest guarantee covers both modes in one sentence: a `look` returns tetel's own output only when the caller named it. That is not a weaker promise dressed up — it is the same rule `look_grep` is being given, since what the exclusions remove is only ever reached by traversal, and it happens to be a rule `look_path` has always satisfied trivially. A reader with only the printed sentence to go on is then told the thing that actually determines whether they will see a snapshot: whether they asked for one.

*cites: C15*

## No opt-out, and what "explicitly named" costs

There should be no `--include-tetel`. The honest escape hatch already exists three times over, and each time it is reached by naming something rather than by setting a flag: open the file with `look <path>`, search with a tetel path as the root, or use `run`. The second of those is not a concession this design makes but a constraint it is under, since grep suppresses a directory named as the recursion root when `--exclude-dir` matches it, so the flags have to be withheld there or naming a snapshot directory would return nothing at all. The third is the hole the ticket already states and cannot be closed: `run` spawns its argv directly with nothing between the empty-argument refusal and the spawn that inspects the command or the paths it will touch, so there is no place an exclusion could be applied even in principle. A flag would add a fourth route with a property none of these has — it leaves no trace in what the caller named, only in how they configured the call.

*cites: C16*

The hard case the ticket asked about is a root like `docs/design`, which in this repository contains nine entries and not one of them is anything but tetel's own output. Under this rule it is not explicitly named — it is an ordinary directory whose path says nothing about tetel — so the exclusions apply and a search rooted there returns nothing at all where today it returns 1,200,881 bytes. That is a real loss and it is accepted deliberately, because the alternative is to decide that a directory counts as named when everything under it happens to be tetel's, which is a judgement about contents rather than a test on a path, and this project does not let a refusal make judgements. The price is one extra keystroke of specificity: to search across memos, name a memo or a snapshot, not the folder they live in.

*cites: C18*

## What the pin still does

The ticket's sharpest question is whether the non-stationarity actually goes away, and the answer is no — it moves, and moving it is the point. Rendering a second memo into a scratch tree, touching no source, left the matched output of a search for the same symbol byte-identical while changing the exclusion list from one memo pattern to two. So the half the ticket complained about within a run is genuinely gone: an evidence ledger growing during grading cannot perturb a census any more, because the search never reaches it. But the exclusion set itself is a function of how many memos the tree holds, the design writes that set into the search record's label, and the label is inside the pin — so two censuses of one symbol against unchanged source will still pin differently either side of a render. That is not a leak that survived; it is the same fact about the world, moved out of the captured bytes where nobody could see it and into a sentence in the record where a reader comparing two pins is told immediately why they differ.

*cites: C17*

## What happens to the memos already committed

Nothing, and the answer has two halves, both of which can be shown rather than argued. The first is that the change cannot reach the check path at all: two exhaustive greps of the whole source tree find `Command::new` in only `observe.rs` — the grep inside `look_grep`, and `run_command`'s child — and `worldstate.rs`, where it runs git; and `observe::` in only `main.rs` and `mcp.rs`, which build a request and dispatch it, and `facts.rs`, where the single occurrence sits in a doc comment. Every other file in `src/` contains neither string, so nothing on the check or render path calls into the observe module or spawns a process. The second half is that there would be nothing to change even if it could: the `tetel fact` module states that extent, output and pin are set once at mint time and never appear in a revision event at all, so no code path exists that could rewrite them. The three committed memos keep the extents and pins they were minted with, whatever a `look` would do today.

*cites: C8*

That much is an argument from the code, so it was also run as an experiment, against the one input the mechanism would actually consult. `tetel check` was taken over all three committed memos while `docs/design` held three snapshot directories, and again after this memo was rendered into the same directory, making four — a change in precisely the set of artifacts an exclusion set is computed from. All three came back byte-identical: same exit code, same length, same hash of everything they printed. A reader who wants the strongest form of the answer has it there, since the experiment would have caught a dependency the greps above could have missed.

*cites: C19*
