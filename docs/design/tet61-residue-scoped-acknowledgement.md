# A residue-scoped acknowledgement for prose-revised-since-proof

All source observations below were taken against one worktree state: branch `tet30-prose-revised-since-proof` at commit `c821b94`, the commit that shipped TET-30's `prose-revised-since-proof` residue. The pin record at the head of this memo's evidence captured `git status` printing nothing at all. No tracked file was modified afterwards; nothing here was implemented. The tree has since gained exactly three paths, all of them this work's own output and all untracked: the memo, its snapshot, and its evidence ledger.

*cites: C1*

## What the residue actually computes

TET-30's listing is worth restating precisely, because the acknowledgement designed here has to key on exactly the quantities the listing keys on, and no others. For each non-heading block with a non-empty citation list, the check derives an anchor — the latest moment at which any of the block's cited claims first entered proof — and a block timestamp, which is not the time of the block's last edit but the time at which the block's *current* text-and-citation pair first appeared anywhere in its history. The block is listed when the pair postdates the anchor. None of these three values is stored; all are recomputed from the event logs at check time.

*cites: C2*

## What changes, and what it costs

Stated upfront, before the argument that gets there: the discharge is a new workspace event in its own append-only log, keyed on the block's current text, its citation list, a digest of each cited claim, and the identity of the workspace that minted it — suppressing the listing exactly while all of that still matches what the check recomputes. A tenth file therefore ships in the snapshot and a new event schema exists, falsifying deliberately the sentence TET-30's memo ends its implementation-surface claim with. The payment is bounded, but by three properties rather than the two an earlier draft claimed, and only two of them come free: a predating build never opens the new file, and the ack log only grows. The third had to be added, because a memo is not bound to the workspace that rendered it, and without the identity component a snapshot can carry acknowledgements no workspace on the machine ever made. The cost also has two shapes, not one. Ordinarily an older build over-reports a line a newer one suppresses. But because a corrupt ack log reddens, one malformed line makes a new build exit 1 where an old build runs clean — a disagreement about the machine partition rather than about a listing. `check` names the binary behind every report it writes, so either divergence is attributable; what that does not cover is a reader holding a single old report, with nothing in it to suggest an acknowledgement exists. For them the answer is the log itself, plain JSON lines beside the memo, readable with no tetel at all.

*cites: C16, C8, C4*

## The residue nobody can honestly clear

Now the problem that buys all of that. TET-30 names two acts that clear a listing, and for the case this design is about — an edit that corrects the prose and touches no claim's proposition — neither describes what the author did. Restoring the text puts the typo back. The other act splits. Revising a cited claim so its new wording can be graded means changing a claim that is correct, and it is worse than merely expensive: out-of-proof is a machine-check disjunct and this residue is not, so that route turns a green run red and keeps it red until another grounding pass lands, in order to silence a line that by construction never failed anything. Adding a citation to a freshly minted claim is cheaper — an ungrounded claim is human-owed, so nothing reddens — but it still means inventing a claim the paragraph never needed and buying a pass to grade it. An author who reads their paragraph against its claims, finds it faithful, and has nothing to change is left with no honest act at all. That is the defect: not the listing on first appearance, which is informative, but its permanence after the human act it asks for has been performed.

*cites: C5*

## Where the event lives, and what it costs

The sketch left the event's home open between `prose.jsonl` and a sibling log. The evidence closes it, and not on grounds of taste. `ProseEvent` is an internally-tagged enum over two variants, and the workspace's line reader turns any single unparseable line into an error over the entire log. A third variant is therefore not a compatible addition: I wrote a scratch workspace whose prose log held one ordinary `Create` followed by one `Ack`, and the build at this pin refused the whole file — including the `Create` it understood perfectly well. Every older build encountering such a snapshot would lose its ability to read prose at all, which is a far worse outcome than the residue line this design exists to clear. The field-level `#[serde(default)]` precedent already in both variants does not extend to a new variant.

*cites: C3*

So the event lives in its own append-only log, `acks.jsonl`, and the snapshot manifest gains a tenth entry. Three properties, between them, make the failure direction one-way, and the third is the one I had to be shown twice. The manifest is the first: it is an explicit enumeration precisely so that shipping a new workspace file is a decision rather than an accident, so a build predating the entry never opens the file and prints exactly the listing TET-30 shipped. The second is that the ack log only grows, which holds cheaply here because the file does not exist yet: nothing in the tool today can remove or truncate a file it has never heard of, its only writer will be an appending verb, and no withdrawal verb ships. That was where an earlier draft of this section stopped, and stopping there was wrong. Monotonicity is a property of one workspace's log; the mechanism runs over a snapshot. Nothing binds a memo to the workspace that rendered it — the flag is free on every invocation — and the writer skips a file the current workspace lacks rather than removing it. So render a memo once from a workspace holding an acknowledgement, then again from a workspace that never held one — a rebuilt state directory, a second machine — and the old ack log survives beside the new prose and claims. That is a superset, not a prefix, and it suppresses a block the true state would list, silently. The third property closes it: the ack records the identity of the workspace that minted it, and suppression requires that identity to match the one the snapshot ships. A log from elsewhere is then void rather than honoured, and the failure returns to over-reporting.

*cites: C4*

## What the reader sees

The brief called deletion and annotation both doctrine-compatible, and they are not equally good. Deletion loses a distinction the crate elsewhere insists on keeping: a report from which an acknowledged block has vanished cannot be told from a report on a memo where no post-proof revision ever happened, and this is a tool whose no-rows path exists precisely to say that two states which happen to both be quiet are not the same state. The cost of printing is also already paid — the entry format carries an author's own reason verbatim today, under `revised because:`, with the source comment insisting it is never paraphrased and calling it the most actionable line the entry has.

*cites: C6*

So an acknowledged block moves rather than disappears. It leaves the group under the "prose revised after the claims it cites settled" preamble — which is what makes the acknowledgement feel like a discharge and not a footnote — and reappears under a single collapsed bullet listing, per block, its id, its line in the document, when it was acknowledged, and the author's own words for why. Because the reason and the timestamp are recorded but not keyed, more than one ack can match a block at once, and the entry prints the earliest of them: that mirrors the trigger's own use of the earliest event bearing the current wording, and it shows a reader the moment the discharge was first made rather than the latest restatement of it. The collapse itself is the crate's habit: the residue's preamble is one document-level bullet, adopted on the stated ground that a constant repeated per row buries what is specific to this document. Leaving the entry in place with an annotation stapled to it would keep the demand standing after it had been met, which is exactly the condition that teaches readers to skim the partition.

*cites: C7*

## The acknowledgement, and the clause that had to go

The event records the block, the block's current text and citation list, a digest of each cited claim's proposition as it stands at that moment, the identity of the workspace minting it, and the author's verbatim reason; it carries a timestamp because every workspace event does. A listing is suppressed exactly when some ack for that block matches all of that, byte for byte, against values the check recomputes — the digests included, and the identity against the one the snapshot itself ships. One detail here is easy to get wrong and I got it wrong first: the digests are taken over the claim as `claims.jsonl` holds it, not over the ledger-derived proposition the in-proof test must use. Those two strings differ — rendering replaces embedded newlines with spaces and importing trims the cell — so keying the ack on the trigger's digest would make any claim with an embedded newline or edge whitespace permanently unackable, silently. Both sides of the ack's comparison read the same source, and the snapshot already ships it. No timestamp is compared anywhere in the predicate.

*cites: C8*

The sketch also wanted the ack's timestamp compared against the recomputed anchor. Working through when that comparison could ever decide anything showed it cannot. The rule is only ever consulted for a block the trigger has already listed, and listing is precisely the statement that the block timestamp exceeds the anchor; the ack is appended afterwards, to an append-only log, by the same workspace and the same clock function that stamped the prose event. Barring a clock set backwards mid-session, the ack timestamp is above the block timestamp which is above the anchor, so the clause is true every time it is asked. Removing it is not a simplification for its own sake — it leaves the suppression predicate with no timestamp comparison anywhere in it, and so the acknowledgement, alone among the moving parts here, does not inherit the two-clock bound that the trigger's own preamble has to print.

*cites: C9*

## Invariants, and the mutations that redden them

Three properties are worth stating as invariants with tests, and each has a specific mutation that should turn its test red. Any later edit to the block's text or citations voids the ack, since both are in the key — weaken the comparison to text alone and a citation-only revision, which TET-30 deliberately made list rather than clear, would slip through an old acknowledgement. Any change to a cited claim's proposition voids the ack, since the key carries that claim's digest — drop the digests and an acknowledgement survives a rewrite of the very claim the paragraph was read against. And for a memo whose snapshot carries no acknowledgement log, the residue reports exactly what it reports today, because the line reader treats a missing file as an empty log; make that an error instead and every memo rendered before this design would stop checking. That third invariant is deliberately stated over the residue's findings rather than the report's bytes, because this same design adds lines to the non-coverage list, which prints unconditionally and so changes the bytes of every report the tool will ever write. It is also about the snapshot and not the workspace, which is worth saying explicitly rather than leaving to be inferred: the check never sees a workspace.

*cites: C10*

Underneath those is the property that makes the rest cheap to reason about: the acknowledgement is a filter applied to the trigger's output, never an input to it. The set of blocks a reader is asked to act on can only shrink, so the design cannot invent a demand. A stale ack and an unmatched ack both simply fail to suppress, which is indistinguishable from no ack at all. A corrupt one is the case I first waved through and should not have. The line reader turns any bad line into an error over the entire log, and the one place this crate swallows that silently — the prose log at check time — defends the silence with a premise that does not transfer: that a corrupt prose log has already reddened provenance before the check gets there. Keeping acks out of `render` is precisely what makes that false for this file. So an unreadable acknowledgement log has to redden, joining the existing rule that drift and an unreadable snapshot are machine failures because both are objective contradictions decidable without a human. That is the single point where this design touches the machine partition, and it touches it for corruption of the record rather than for anything an acknowledgement means. It is also worth being clear what the digests do not buy: keying on them does not close TET-30's conceded blind spot for prose that ships alongside a claim revision. It only stops an acknowledgement outliving the state it attested to.

*cites: C11*

## Minting it, and what the verb can and cannot refuse

There is exactly one verb — `prose --ack <id> --why <text>`, on both front ends — and, as the section on withdrawal explains, deliberately no second one. It is added to the shared request shape the CLI and the MCP server already funnel through, and here I have to correct something an earlier draft of this memo asserted: that shape is necessary for the two front ends to agree, and it is not sufficient. This verb is the case that proves it, twice over, both times about text. An acknowledgement carries none, but the MCP parameter struct declares text as a plain required string while the CLI declares it optional — so an ack over MCP is refused by deserialisation before any of the tool's own refusals are reached, and the same ack over the CLI sails through. Relaxing that field is part of this design. But relaxing it is not enough, because an absent `--text` on the CLI does not mean absent: both text-consuming arms resolve it through a helper whose empty case reads standard input. Left alone, an acknowledgement with no text would sit there blocking on stdin. So `--text` has to be refused outright in this mode, and the ack arm placed where it can never reach that fallback.

*cites: C12*

There is a second thing each front end does that this verb must not inherit. Mode is selected by an if/else-if chain that builds one request variant and silently drops whatever inputs that variant has no field for, so an ack combined with `--text`, `--revise`, `--heading`, `--level`, `--cites` or `--before` would discard one without a word — the same shape as the defect this crate already had to fix once, when citations were accepted alongside a revision and thrown away. All six have to be refused, and `--level` is worth dwelling on because I left it out and an attack pass had to put it back. On the CLI it is its own flag, consumed by the heading arm but selected by `--heading`; over MCP the two are folded into a single field that is selector and value at once. An enumeration written while looking at the MCP shape cannot see the CLI's seventh flag. Of the ack's remaining refusals only two already exist: the block must exist, and `--why` must be non-empty, the latter on literally the test that backs the revise verb's insistence that revisions explain themselves. Three are new, because creation is deliberately ungated — refusing a heading, refusing an uncited block, and refusing a citation that names no claim. Each earns its place: a listing exists for neither a heading nor an uncited block, and the ack's key is a digest per cited claim, which an unresolvable id cannot supply. One refusal that might seem obvious is impossible. The verb cannot decline to acknowledge a block that is not currently listed, because an authoring workspace holds prose, claims, facts, targets and counters and no evidence records whatsoever — grading records live beside the rendered memo — so at mint time there is no anchor to compute. Nor is it wanted: acknowledging an unlisted block suppresses nothing.

*cites: C12*

## The lifecycle across render

Because the residue is computed against a snapshot and the snapshot is written by `render --out`, an ack minted after a render is invisible until the next one. That sequencing is not new and it is not this design's to fix: everything the check sees about a workspace it sees through the snapshot. What is this design's to decide is whether the acknowledgement changes the memo's bytes, and it must not — the determinism of `render` in the workspace alone is what makes a drift finding mean anything. Keeping acks out of the rendered output turns the extra render from an annoyance into a useful signal: it rewrites the snapshot in place and leaves the document byte-identical, so the discharge lands in version control as a change to the record with no change to the argument. That is a true description of what an acknowledgement is.

*cites: C13*

## Withdrawal, supersession, and an append-only log

Supersession asks nothing of the design. Matching is existential over keys, so a later ack with a different key simply does not match, and a duplicate ack for the same key cannot change whether a block is suppressed. Withdrawal is the harder question, and I have been wrong about it in both directions. I first designed an `Unack` event, on the reasoning that an author who acknowledged too quickly and cannot yet rewrite the paragraph would otherwise have nothing to say. Then I removed it, on the reasoning that a negative event is uniquely droppable — and that reasoning survives, though it turned out to matter for a different reason than I gave. Declining the verb is what keeps the ack log monotone, and monotonicity is what makes a stale snapshot copy a prefix rather than an arbitrary earlier state, which is the whole one-directional guarantee of the section above. An `Unack` would have broken it: a render by a build predating the log leaves it where the last knowing render put it, so a withdrawal appended afterwards vanishes while the acknowledgement it cancelled survives — the one path by which a negative event is lost and a positive one is not. And the decision stands on a second leg that was always the stronger. The case an `Unack` protects is not symmetric with the defect this design exists for: an author who now believes the paragraph is faulty can repair the paragraph, which voids the acknowledgement by changing its key. That is an honest act, and it is the one they should be taking. TET-30's defect was precisely that a correct paragraph left its author no act at all.

*cites: C14*

## The implementation surface

Eleven symbols change, and the whole-worktree census of each is what lets that be said rather than hoped. On the check side the obvious four: the rule function takes the acks as a further input and returns two partitions instead of one list, bounded by there being exactly one production call site among its thirty-three; the findings field gains a sibling; the snapshot manifest goes from nine entries to ten; the non-coverage list gains entries. The snapshot writer, which an earlier draft would have changed, is untouched. Then three more that an attack pass had to find, because they are the price of reddening a corrupt ack log: a new findings field reddens nothing by itself, so the machine-check disjunction gains a term, the failure count — a hand-written sum linked to that disjunction by nothing but discipline — gains another, and the literal naming the machine-checked categories gains a twelfth. The authoring side added four more across two passes: two enums consumed by exhaustive matches, a parameter type where the front ends had already drifted on whether text is required, and a flag declaration living on the variant rather than the dispatch arm. And then, on the last pass, three enumerations of those same categories that no census reaches at all — the README, the MCP tool description that agents read as the schema, and the printed human-owed headline that TET-30 itself had to hand-edit to announce this very residue, and that the acknowledged bullet obliges someone to edit again. The honest summary is not the count. It is that this memo has now been short by one on three separate enumerations, found by three separate passes, and that an implementer should re-derive every list here rather than trust it.

*cites: C15*

## What the acknowledgement does not establish, and where per-citation attribution goes

Three lines are owed in the printed non-coverage list, on the list's own standard that a deliberate exclusion earns its own line because a refusal that fired reads too easily as coverage it never claimed. One: an acknowledgement records that a human said they re-read the paragraph against its claims, and nothing verifies that they did or judges whether the paragraph is faithful — after an ack, the tool's silence is the author's assertion and not the tool's finding. Two: an acknowledgement minted after the last render is not in the snapshot the check reads, and suppresses nothing until the memo is rendered again. Three, for the reason the closing section gives: a snapshot's acknowledgement log is never re-rendered, so a hand-edited one is invisible to the drift check.

*cites: C17*

The advisory recommendation that per-citation attribution be folded into the ack rather than into the trigger is accepted, and it is worth being blunt that the fold does not go far. The residue's own non-coverage list already concedes that whether a paragraph was examined against an earlier-settled co-citation is answered by no listing, and the acknowledgement does not answer it: the ack is per block, its key records only that every cited claim's digest was what it was, and the sole place a per-citation judgement can live is inside the author's verbatim reason, which nothing should parse. So the acknowledged bullet prints the block's cited claim ids beside that reason, letting a reader pair the author's words to the citations themselves, and the non-coverage entry stays exactly where it is.

*cites: C18*

## Migration, and one question left open

When the full obligation ledger lands, these events are the discharge records it would consume for this residue class, and the log moves into it unrewritten. That works because nothing in an ack is specific to the check it discharges: it holds a block id, a text, a citation list, a digest per cited claim, a reason and a timestamp, and none of the quantities the rule derives — not the anchor, not any claim's first proof, not the block timestamp, not even whether the block was listed. The general ledger needs the events as they stand plus a rule that reads them, which is a re-homing and not a rework.

*cites: C19*

One line on the separate question of warning an author when they revise prose whose claims have settled: this design does not settle it and does not depend on it, but it does change its economics, since such a warning today could name no act and afterwards could name this one. Whether it is worth building stays a measurement question, unanswered here.

*cites: C20*

One thing remains to be said, and it belongs with the decision to keep acknowledgements out of the rendered bytes. Drift is decided by re-rendering the snapshot, and `render` reads exactly five of the nine files a snapshot ships — prose, claims, targets, transplants and facts. The other four are shipped and never re-rendered, so tampering with them is not drift, and one of those four is the identity file, which already decides whether the report calls a claim self-grounded or independently grounded. An acknowledgement log joins that group rather than founding it. A hand-edited snapshot ack log is therefore undetectable by drift, and the honest response is a non-coverage line rather than a bespoke mechanism: guarding acks alone would leave the four existing members unguarded while implying they were not. That is the last of this design's costs, and like the others it is meant to be read rather than absorbed.
