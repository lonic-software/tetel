# # TET-28 design: the modification-target census, and where its refusal can decidably live

All code observations in this memo were taken against the tetel repository at commit 57bd0e2 ("ci: make the guards authoritative for the repository, not just for one editor"); at the start of authoring the working tree was clean, and the memo you are reading plus its snapshot are the one addition this workspace makes to it. TET-28 asks for a refusal: a memo that tells an implementer to modify a symbol must carry a repo-wide census of that symbol, captured by the tool rather than typed, or the memo does not render. The motivating defect, as the ticket reports it from a private project's review trail and described here only by its shape: a memo recommended modifying a function and spent a repo-wide negative about its callers, while the author's actual caller sweep — honest in its own fact — was scoped to a single file; per the ticket, one workspace-rooted grep would have landed on a second production gate with a different mechanism, and the miss instead survived five review rounds before both attack passes found it independently. This memo settles the two questions the ticket leaves open — what the trigger is and whether it is decidable, and what "workspace-rooted" means decidably — and reaches a design that keeps the refusal format-level.

*cites: C1*

The answer, up front. The refusal can be built on-charter, but only after two reformulations the ticket does not spell out. First, the trigger cannot be "the memo recommends modifying X" — tetel's record model has no notion of a recommendation, and detecting one in prose is the heuristic the charter forbids; the trigger is an author-declared target record, with under-declaration handled by visibility rather than detection. Second, the rooting requirement is not checkable against what look --grep captures today: a grep that finds matches records nothing about where the search was rooted, so the rule needs a small capture extension before it needs a check. With both in place, the refusal reduces to byte comparisons over tool-captured strings — existence and rooting, exactly as the ticket asks, and nothing else.

*cites: C14, C7, C2, C4*

## ## What "workspace-rooted" can decidably mean

Start with the second question, because its answer constrains the first. The ticket's rule requires each modification target to cite a fact whose captured extent is a workspace-rooted `look --grep <symbol>`, captured by the tool rather than typed. TET-5's per-observation markers were believed to make "repo-wide or one file" decidable for the first time. That belief is half right, and the half that fails is the half a census lives in. When a grep finds matches, the captured extent is one entry per matched file, keyed on the matched file — deliberately not on the search root or the command line — so a repo-wide search and a single-file search that matched the same files are byte-identical in the record. A census of a symbol you are telling someone to modify always has matches, because the definition site matches. As captured today, the rooting half of TET-28's rule has nothing to check.

*cites: C2*

The zero-match case shows what decidable rooting looks like, because it is already decidable: a no-match grep records one entry keyed on the resolved search root, with its working-tree marker resolved from that same root, so "was this negative bounded by the whole worktree" is a comparison of two tool-captured strings on one entry — the key against its own world_root. The fix is to make the positive case capture what the negative case already captures: every `look --grep` additionally records one root-level search entry (resolved search root as key, pattern and match-file count in the label, marker from the search root) beside the per-file matches. "Workspace-rooted" then means exactly one thing in both cases: the search entry's key equals its own world_root — two strings produced by the same call from the same canonicalized directory, with no author-typed input on either side. This is a capture extension, not a check bolted over missing data, and it is the load-bearing prerequisite for everything below.

*cites: C3, C4*

Two details of the record model decide how that search entry must be stored. First, an observation's kind does not survive minting — the fold keeps only key, label and the two marker halves — and the grep pattern survives only inside a human-readable label, which an author-chosen pattern could make ambiguous to parse. So the search entry carries its kind and its pattern as structured fields on the extent entry itself, added the way world_root was added: serde-defaulted, with the empty value meaning "minted before this field existed and therefore not eligible", never guessed about. A fact minted by an older build can consequently never satisfy a census requirement, and the remedy is the cheap one the ticket already prices: re-run the grep. Second, the snapshot ships facts.jsonl with full extent entries, so check reads the same structured fields from files every snapshot already contains — and since no authoring surface lets anyone supply an extent by hand, the pattern, the root and the marker on a census entry are all tool-captured by construction, which is what the ticket's "captured by the tool, not typed" clause actually requires of the storage.

*cites: C5*

The predicate has one soundness worry worth retiring now: it compares a filesystem-canonicalized path against git's own spelling of the toplevel, and those are produced by two different tools. A live probe against this repository shows them agreeing byte-for-byte, and the failure mode if they ever disagree is the right one — inequality can only deny rooting, so a spelling divergence refuses an honest census loudly instead of accepting an unrooted one silently. Two hardenings close the gap: look_grep itself compares the canonicalized search root against the marker's root at capture time and stores the search entry's key in the marker's spelling when both name the same directory, leaving check a pure byte comparison; and the agreement is pinned by a test rather than assumed, since one probe on one machine establishes the common case, not an invariant.

*cites: C10*

## ## The trigger: declaration, not detection

The ticket's rule as written — refuse "a memo whose recommendation names a target" — has no decidable trigger, because tetel has no notion of a recommendation. Verified against the record types: a claim is a proposition with fact citations, a prose block is text with claim citations, and nothing on either surface types a record as an instruction — prose creation is deliberately ungated because prose is where the author talks, not where they are audited. So the rule's subject denotes no set of records a check can enumerate, and deciding from English that a sentence tells an implementer to modify something is a heuristic read, which the charter forbids as a refusal trigger. The obvious repair — trigger on any symbol a claim's proposition mentions — is not merely off-charter, it is already measured dead in this repository: the note-outside-extent work tried string-matching symbol references and rejected the detector because it flagged a legitimate quotation while missing both real overreaches. Naming a symbol the code you read calls is normal; concluding about it is the failure; the two are not distinguishable by string matching, and a refusal wired to that detector would make honest memos unwritable. One consequence for the roadmap: the README's Direction entry for this feature currently reads "a workspace-rooted search behind a claim that names a symbol", which is the mention-triggered phrasing, and should be corrected to the declared-target shape when this ships.

*cites: C14, C6*

What is decidable is a declaration. A modification target becomes a structured record — a symbol string plus a citation of the fact that censuses it — created by a new authoring verb and rendered as its own section, the way the evidence ledger and Facts table already render structured records without generating prose from fields. The refusal then never reads English at all: it fires when a declared target's cited fact carries no qualifying census entry, which is an objective contradiction between the document and the record it claims to rest on — the exact principle the machine partition already states for provenance drift, and the README's own example of the one decidable refusal shape, "you did not point at your evidence". The disposition follows the project's report-versus-refuse discriminator from the other side: the note-outside-extent check stayed human-owed because only a person can tell context from conclusion, but for a declared-and-uncensused target nothing is left to tell — the remedy is singular. Run the workspace-rooted grep for that symbol, mint the fact, cite it; or withdraw the target.

*cites: C7*

Declaration moves the vacuity question to under-declaration, and the honest answer is that no refusal can reach it: deciding that a memo recommended something it never declared is the same heuristic read of prose the trigger just rejected. The design's answer is visibility rather than detection, in two places. First, the section never disappears: once a workspace declares any target the section renders, and once any claim exists it renders even when empty, as "Modification targets: none declared" — so a memo full of tell-the-implementer language with an empty census section shows its hole to every reader, instead of an undeclared target being an invisible omission. Second, check's standing non-coverage list — whose first entry is already "dependents that never declared themselves" — gains the census's own blind spot, stated as such. The ticket offers a further reason to assess the risk as small: its review protocol's adversarial pass puts every tell-the-implementer claim in scope unconditionally. That is a property of an agent definition outside this repository, not of tetel, so this design records it as the ticket's premise and deliberately does not lean on it — the rendered hole and the printed blind spot carry the visibility argument on their own, for any consumer of the tool, with or without that protocol around it.

*cites: C8*

The refusal lives at the earliest surface that can decide it: declaration. `tetel target` refuses to create a target whose cited fact has no qualifying census entry — the same authoring-time shape as `tetel fact` refusing on an empty pending buffer. A fact's extent is immutable once minted and a target immutable once declared, so this one refusal makes "every declared target is censused" a workspace invariant, and render needs no refusal of its own for workspace-authored documents: its job is to emit the section. What render cannot vouch for, check re-verifies — the rendered document against its own snapshot, reported as [uncensused-target] in the machine partition's scope line — which is what catches a hand-authored or tampered document that never passed through the refusing verb. Like the other snapshot-dependent findings, that check runs only when a snapshot ships; without one, target rows are reported human-owed as unverifiable, consistent with the standing choice that a missing snapshot is human-owed rather than a machine failure. The verb itself must be one dispatch shared by CLI and MCP, the pattern look and fact already use, because this render path has already recorded one CLI/MCP drift on a duplicated act.

*cites: C9*

## ## The rule, precisely

A modification target is an append-only record: a symbol string plus the id of the fact that censuses it, created by a new authoring verb (`tetel target <symbol> --cites F#`), withdrawable but not revisable — a changed symbol is a different census, so the honest edit is withdraw and redeclare. A declared target is censused when its cited fact's captured extent contains a search entry whose kind marks it as a whole-search record, whose pattern byte-equals the declared symbol, whose key byte-equals its own world_root, and whose world_root is git-backed — neither the no-git sentinel nor the empty value that marks an entry minted before the fields existed. Pattern byte-equality is the only sound comparison on offer: grep receives the pattern verbatim, so "pattern contains the symbol" would accept a search whose pattern embeds the symbol in a longer string and finds strictly fewer of its occurrences, and anything wider means deciding containment between regexes. Symbols that are not literal in the system grep's dialect are a stated limit, not a case the check judges. Everything else about the census — what the matches say, whether they were read, whether the root was the right tree — is deliberately outside the predicate: the refusal is about existence and rooting, never content, because content is the insincere-examination ceiling this project has already registered as out of reach.

*cites: C11, C12*

## ## What the census does not see, printed rather than implied

check's report already carries a standing non-coverage list, printed item by item, and this feature adds its own blind spots to it rather than leaving them implicit. A textual census cannot see dynamic dispatch, re-exports or aliased imports, or callers assembled by macros and string concatenation. Its traversal is the system grep's — tetel shells out precisely to avoid owning a subtly different regex dialect — so the platform's rules for symlinked directories and the binary-file skip bound what a repo-wide search physically visited. Rooting establishes where the search started, never which tree it should have started in: whether the censused root is the tree the memo designs against remains a reader's question, answerable from the per-root tree-state report the check already prints. Whether anyone read the census is the insincere-examination ceiling: a census is a list of sites, not an understanding of them. And under-declared targets are invisible by construction — the hole in the rendered section and the non-coverage line are their only trace.

*cites: C12*

One further limit deserves its own line rather than absorption into the ceiling above, because it bounds the artifact and not the reading of it. A census enumerates call sites; it does not enumerate the modes those sites select. The captured output per matched file is the matching lines only, so an argument value that chooses between materially different mechanisms — a None against a Some, a flag, a mode enum — is sometimes visible on a match line, never enumerated, and absent entirely when it arrives through a variable, a default, or another line of a multi-line call. This is the motivating defect's shape one level down: that finding was a second gate nobody enumerated; this is a second mode nobody enumerated, at a site the census did find. It is distinct from the insincere-examination ceiling because sincere reading of the census does not cure it — the partition is not in the census to be read, and a reader must leave the artifact for the callee and each call's context. It changes nothing in the design: extracting argument values would mean parsing call expressions, per-language knowledge the language-agnostic-by-construction doctrine exists to exclude, and a value-surfacing census would still need the same declared-target trigger — so the trade is named and declined. What it costs is one more printed non-coverage line: the census gets an implementer to the door of every textual call site; it does not say what happens inside any of them.

*cites: C15*

## ## Sequencing, and what this memo does not decide

The ticket asks that this ship before any TET-27 co-evolution run, on the argument that findings the census would have surfaced must not be double-credited to a prototype, which would make that run's "would existing machinery have caught this anyway" kill-arm unevaluable. The premise of that argument lives in the tickets and the private review trail, not in this repository, so this memo does not grade it; what this memo can establish is that the sequencing costs nothing. The feature's surface is one recorded entry in the grep path, two serde-defaulted fields on the extent record, one new record type and verb, one rendered section, one shared refusal, and one machine check with its printed limits — each an extension of a mechanism cited in this memo's facts, and none of them a code-to-graph link, a commit reference, or dependency propagation, the mechanisms the TET-27 ticket describes as its subject. Shipping first is therefore safe whether or not the double-crediting argument is right, and the design was not bent to accommodate it. What this memo deliberately does not decide: any implementation detail beyond the record shapes and predicates above, and any widening of the trigger — in particular, no future measurement of a mention-based advisory should be allowed to harden into a refusal, because the measured evidence in this repository says that detector cannot tell quotation from conclusion.

*cites: C13, C6*
