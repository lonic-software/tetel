# TET-84: a verification that did not run says so

Every observation in this memo was taken against tetel at 74d4622d, the tip of origin/main after PR #30, with no tracked file modified. The first two parts of TET-84 are merged. PR #28 made a verification that ran out of budget report `timeout` rather than `unavailable`, and PR #29 raised the default budget. This memo is the third part: what the author is told when a verification does not complete.

*cites: C1*

## What this design delivers

Three changes to the `verify` object that every `fact`, `claim` and `prose` reply carries, and nothing outside it. The reply that delivers a failed verification says why, through the record's `detail`. Model or provider reply text is never included. Under the three failure statuses, `guidance` says the mint was not checked instead of describing findings that do not exist. A new `unverified` key names the mints whose latest verification failed. It stays on every reply until each of them is re-verified, withdrawn, or belongs to a verb no longer verified. The tool description and docs/verify.md change with it.

*cites: C3, C5, C6, C7*

## The defect

A verification runs after its mint has replied, and its result arrives on some later reply: one record per call, oldest first. Calls that overlap can each show the same record. When it ends `timeout`, `unavailable` or `unparsable`, the reply that delivers it carries the status and nothing else about it. The record's `detail` stays in the log, because `block` only ever inserts a detail for `unauthorized`. The `guidance` beside it is the constant written for findings, which tells the author that a model found their text inconsistent with the evidence and asks them to read a quoted span that is not there. Once the record has been delivered, no reply mentions the mint again. An author who misses one field has no way to learn that the mint was never checked.

*cites: C2*

## Decision 1: the delivered record says why

The record already knows why it failed. The change is that the reply delivering a `timeout`, `unavailable` or `unparsable` record carries its `detail`. On those records the detail belongs to the failure. Only the classify and check legs can end a verification, each returns as soon as it fails, so the leg that failed is the last one that ran. Most causes are fixed text, a status code, a transport error, a byte count or a budget. Under `ok` and `gated` no detail is delivered. There the field holds whatever leg last wrote it, possibly a draw that was retried and then succeeded, and the `*_incomplete` keys already say which leg did not finish. `unauthorized` keeps its current detail, which names the missing configuration. Four of the twenty sources quote the model's or the provider's own reply. Those quotations stay in the log, for the reason the module already withholds an unverified quoted span. A reader shown text that looks like evidence will go and check it, and this text is not evidence.

*cites: C3*

The quotations are split off where they are written rather than trimmed from the finished string afterwards. Each of the four sites will write its explanation to `detail` and the quoted text to a separate field that only the log and `verify-report --spans` read. Three of the sites format an excerpt directly. The fourth, `parse_assertions`, returns its label inside an error string that `run` stores, so that function will return the explanation and the label separately. The split also fixes a quiet fault in `verify-report`. The report groups identical `detail` strings, and a string ending in a per-reply excerpt is never identical to another, so today every such failure prints as its own line, mostly excerpt. The guarantee is per site, not structural: a fifth site could format reply text into `detail` and nothing in the type would stop it. The four tests below pin the four sites that exist.

*cites: C4*

## Decision 2: guidance that matches the status

Under `timeout`, `unavailable` and `unparsable`, `guidance` becomes a second constant. It says the mint named by `for_mint` was not checked, that a missing `findings` means nothing was compared, and that `detail` says why. It also says that an unchecked mint blocks nothing and is not a request to change it. The constraint behind that is real. Repeating the same text starts no new verification, and grounding recorded against a claim's wording stops counting once the wording changes. Rewording a claim to clear the list would buy a model's opinion at the cost of the claim's grounding. `ok` keeps the existing constant, since it is the one status whose reply carries findings. The other statuses (`queued`, `skipped`, `off`, `gated`, `unauthorized`) are also misdescribed by the findings-shaped text, but none of them is a check that was attempted and lost. They are left alone and listed as a residual.

*cites: C5*

## Decision 3: the unchecked mints stay named

A status delivered once is easy to miss, so the failure has to persist until it no longer holds. `unverified` carries `count` and up to ten mint ids, and it rides on every reply that carries a `verify` object while verification is enabled, including replies on a verb that is not itself verified. A mint is on the list when its verb is still verified and its latest verification failed. A mint of a verb the author has stopped verifying drops off, since nothing would ever clear it. "Latest" means highest revision, not last in the log. The log is in completion order, and a revision's verification can finish before the one it replaced. So `Subject` and `Record` gain the mint's revision count, which each verb's ledger already keeps and which never decreases. Two overlapping revisions of one mint can read the same count, since nothing serialises the handlers. A tie goes to the record later in the log. Records written before the change have no revision and sort behind those that do. A revision that starts nothing leaves the older failure standing, which is the truth: the current text is still unchecked. The tally comes from the log that `peek_delivered` already parses on every call, so it adds no read of verify.log. The claim ledger is read only when a failing mint is a claim, which is the one kind that can be withdrawn.

*cites: C6*

## Documentation surface

The status vocabulary is stated in two places, and both change with the payload. The `claim` tool description gains one sentence: a delivered failure carries `detail` saying why, and `unverified` names the mints still unchecked. In docs/verify.md, "What comes back" stops tying `detail` to `unauthorized` alone. It says `detail` also carries the cause under the three failure statuses, and not under `ok`. It adds `unverified` to the keys that appear only when they have something to say, noting that the key appears even on a reply whose own verb is not verified and lists only mints of verbs still verified. And it notes that `guidance` differs under the three failure statuses.

*cites: C7*

## Falsifying tests

Each test names the revert that turns it red. Three cover `detail`: a planted `timeout` delivers it, an `ok` with a failed refuter leg does not, and a gate failure followed by an LLM-call timeout delivers the timeout's cause, not the gate's. Four cover the reply-text split, one per site, with every later leg switched off so that no later write can mask the site. Each drives a sentinel through a reply body and asserts that the sentinel is in the record's log field and absent from its `detail`, whatever status the record ends with. One covers `guidance` across the three failure statuses and `ok`. Five cover `unverified`. The first is a planted log that mixes a recovered mint, two failures, a withdrawn claim, a failure under a verb no longer verified, and a mint whose later revision's record was appended first; that last case proves ordering by revision rather than by log position. The others check the ten-id cap, absence when verification is disabled and presence on a reply whose verb is off, the two orders in which a legacy record without a revision can meet one that has it, and the two orders of a tie at one revision.

*cites: C8*

## Rejected alternatives

A key outside the `verify` object would separate "found nothing" from "did not look", which are exactly the two things an author must read together. Surfacing unverified mints in `check`, `brief` or the rendered memo would put a non-repeating model call inside the partitions that state what `check` covers. The module header rules that out for this reason. A retry or circuit breaker changes what the verifier does, and this design changes only what it says. A failure rate names no mint to act on and never falls when one is fixed. Refusing the mint would break the verifier's one hard rule: nothing in it can fail a mint.

*cites: C9*

## Deferred and residual

Deferred to TET-100: re-running a failed verification without changing the mint's text. After this change the author is told a mint is unchecked, and can usually clear it only by rewording it or changing its citations. A re-run would write a record at the mint's current revision, and the tie rule already lets the later record stand. Residuals:
- The other five statuses keep the findings-shaped `guidance`.
- Keeping reply text out of `detail` is enforced per site by tests, not by the type.
- A mint minted while verification was off, or could not start, has no record and is never listed.
- A mint being re-verified stays listed under its old failure until the new record lands.
- A transport failure's `detail` carries the HTTP library's error text, which may name the endpoint but never the key.
- A failure delivered for a claim withdrawn since dispatch still shows its status, although the tally omits it.
- A record torn by a crash mid-append is seen by neither delivery nor the tally.
- A prose block revised to cite nothing, or a mint revised while no credential is set, stays listed until a retry path exists, truthfully but uncleared.
- On a failure record, `detail` belongs to the failing leg because that leg ran last, not because the field is scoped per leg.
