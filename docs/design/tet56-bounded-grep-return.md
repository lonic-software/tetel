# TET-56 f3: tetel bounds its own `look` return

This memo designs one change with two halves. `look` decides for itself how much of an observation it returns to the author, and it says what it withheld in two places: in the observation's label, where a later reader of the memo finds it, and in the returned text itself, where the author finds it before writing anything about what they saw. The worktree everything below was read against is pinned: HEAD 81137aa683bdced9bf01a94d34c66b7f4a1758fd on branch tet30-prose-revised-since-proof, with every tracked path unmodified and unstaged and the only entries `git status` reports at all being the eleven untracked files this design itself wrote — the memo, its evidence sidecar and its snapshot directory. So a reader can re-run any of it against the same tracked bytes. Which of those states each individual fact was captured in is not asserted here: tetel records it with the fact and `check` reports it.

*cites: C1*

## ## Where the bound goes

`look_grep` already does the two jobs separately. It runs grep once, then builds `printed` — the string handed back to the author, which today is grep's stdout verbatim followed by a parenthesised exclusion note — and, independently, the pending entries: one `Search` record carrying the root, the pattern and a matched-file count, and one `GrepMatch` record per matched file carrying that file's matched lines. The two are derived from the same stdout but neither reads the other, and that separation is what the bound rests on: out of a bounded call, every entry's captured output, its key and its world-tree markers come back byte-identical to what they are today, so two observations of one root still overlap and a later reader still re-reads the same bytes. What does not stay identical is the extent, the pin and the fact that ships. `facts::mint` copies each entry's label straight into the extent and hashes label, world markers and output into the pin, and this design writes a shortfall segment into the label — so wherever the bound bites, all three differ from what they would otherwise have been. That is the point and not a cost. It is the same property the exclusion note was given when TET-46 chose to list the skipped memo paths rather than count them, so that two searches withholding different things could not fingerprint alike; a bounded search and a whole one should not fingerprint alike either. What makes f3 cheap, and what keeps it inside the ticket's scope, is narrower than "nothing changes": no new record, no second pass over the buffer, nothing read back out of the entries, no signature touched. One number is computed while `printed` is being assembled, and the label is built from that number. The direction matters to whoever implements this — bound first, label from the bound. An implementer who bounds `printed` and leaves the label alone has rebuilt the silent cut this memo exists to remove.

*cites: C2*

## ## Where the shortfall is recorded

The ticket's phrase "in the search label" names a place the bound has to appear, and the reason for it needs stating precisely. A memo's Facts table renders the Extent column as the observation labels joined with `; ` — every entry's label, the whole-search record's and each per-file record's alike — while keys and captured output are deliberately excluded from the document. So a label is the only kind of thing a later reader of the memo can learn a truncation from, and anything recorded only in the captured output is invisible in the artefact this design exists to make honest. Which label is then a second question, and it has a different answer: the search record's, because the bound is a property of the search and not of any one file. The per-file records are built from the full stdout and ship complete however little was returned, and their labels name a file and a pattern and nothing about size, so a shortfall written into one of them would be attributed to a file that did not suffer it. But what all of this establishes is necessity and not sufficiency, and it establishes it for one audience only: the reader of a committed memo. It says nothing about the author, who at the moment they read a return has read no label at all.

*cites: C3*

The author is the other audience, and the label does not reach them in time. `look` hands back `printed` and nothing else, on the CLI and over MCP alike; the label first becomes visible one act later, in the `fact` result, by which point the note asserting over that observation has already been supplied as a parameter of the same call. An author who read a bounded return and then wrote "this is every call site" would have committed the assertion before tetel told them anything had been cut — the design's own defect, reappearing on the surface it exists to fix. So the shortfall is written into `printed` as well: one `push_str` at the end of a bounded return, carrying the same numbers the label carries. The crate already has a spelling for this half. `refuse_incomplete` shortens an undischarged premise to its first line for a refusal message and marks it with a trailing ` …`, applied when and only when something was actually removed. f3 keeps both of those properties — cut on a line boundary, mark only when the bound bit — and adds the one thing that spelling does not carry: how much was withheld. `refuse_incomplete`'s ellipsis records that text was cut; nothing in its message counts what it dropped, and this design's segment does.

*cites: C21, C7*

## ## What the bound is, and where it comes from

There is no honest way to derive the number. The MCP `look` handler receives a workspace, a path, an optional line range and an optional pattern, and hands back `printed` without measuring it; no field anywhere in that call carries a caller's result cap, so tetel cannot learn one at run time. The number is therefore a person's choice, and this crate has already decided how it treats those. `describe_buffer` declined to invent a staleness threshold because "a number chosen here would be arbitrary", and made the underlying fact visible instead. The same shape applies here: the constant is a documented judgement, and nothing load-bearing rests on its exact value — what the design guarantees is that whatever was withheld is named. How it is named is not open in the same way. `refuse_incomplete` already shortens an author's premise to its first line for a refusal message and marks the result with a trailing ` …`, so the spelling is a house convention to be followed rather than a blank page: the number is a judgement, the marker is not.

*cites: C6, C7*

The value proposed is 32 KiB — 32768 bytes — and it is proposed as a judgement, which is the whole of its justification. The single constraint it has to satisfy is that it sit strictly below whatever cap the caller applies, and since tetel cannot observe that cap the only available discipline is to choose conservatively. What can be stated exactly is its effect on the censuses measured here: seven of the nine return bounded, and `target` at 24974 bytes and `label` at 8201 still return whole. A reader who disagrees with 32768 is disagreeing with a judgement, not correcting a measurement, and the design does not change if they win.

*cites: C8*

Two things follow about the unit, and they point in different directions. The constraint is a byte budget, and bytes are not predictable from lines: on this HEAD a single grep output line reaches 1090 bytes, so a bound of "the first 450 lines" would have let a return through at several hundred kilobytes while still calling itself bounded. But bytes are the wrong thing to cut on, because grep's unit is the line `<file>:<lineno>:<text>` — the same unit `look_grep` splits on to build its per-file records — and a return severed mid-line hands the author a fragment that is not a match. So the first half of the rule is: accumulate whole lines, and stop before the first line that would carry the total past the byte budget. There has to be a second half, for a reason the next paragraph takes up.

*cites: C4, C5*

On its own that rule has a hole, and not a hypothetical one — but it is a hole about the first line of a selection, not about a file. If the first line the rule considers is by itself over budget, no whole line fits, and the return is a header with nothing under it and a label truthfully reporting that nothing was shown. A file that merely holds a long line somewhere does not produce that state: the accumulation stops before the long line and hands back whatever whole lines preceded it. Four tracked files in this repository do hold such a line — all of them tetel's own snapshot ledgers, the longest carrying a single line of 905745 bytes — and nothing keeps them out of reach, since a plain `look` refuses only a missing path and a directory and filters nothing at all. In none of the four, though, is that line the first: the over-budget lines sit at positions 11 and 15 of 20, 15 of 21, 2 of 11 and 2 of 10, so a read that begins at line 1 hands back 5, 2, 1 and 1 whole lines rather than nothing at all. What reaches the empty state is a selection that begins on such a line, and `--lines` supplies it directly — `--lines 15:20` on the longest of the four, `--lines 2:11` on another. There the whole-lines-only rule is strictly worse than the silent truncation it exists to replace: a cap that cuts a long line short still hands the author a prefix of it, and this rule hands them none of it. So the rule takes a floor. Where no whole line fits, the return carries the first line cut at the largest character boundary at or below the budget, and both surfaces say it was cut mid-line rather than reporting a line count alone. That gives up something real, and the memo should name it rather than let it pass: a floored return can hand the author a fragment that is not a whole match record, which is the thing the line-boundary rule was chosen to prevent. What survives the cut is the prefix — a cut grep line still begins `<file>:<lineno>:`, so the fragment still says which match it came from — and the whole line is still in the per-file record that ships. Against an empty body that is the better trade, and a bounded return is now never empty when what it bounded was not. In content the design deliberately returns far less than an unbounded caller would, since the budget's one constraint is to sit below a cap tetel cannot observe; in string length it can run a little past its own budget, because the shortfall segment is text a whole return would not have carried and, like the exclusion note, sits outside the measure. What the floor restores is the promise the design actually makes, which was never to return more but to leave nothing withheld without saying so. The cut itself has to be spelled out rather than borrowed: nothing in `src` cuts a string at a byte budget today, and these long lines carry multi-byte characters, so the offset is snapped down to a character boundary instead of being taken raw.

*cites: C5, C8, C22*

One boundary question has to be settled before the label can be specified, because the label reports a number and the number needs a referent: what exactly is being measured. `printed` is not simply grep's output. The parenthesised exclusion note is pushed onto the end of it as a separate segment, on the matching and the no-match branch alike, so a budget applied to the assembled string would eat that note first — it is last. That would be precisely backwards. TET-46 put the note into the return because silence about an exclusion is ambiguous between nothing having been hidden and nobody having said so, and the return that most needs to name what it withheld is the one already withholding the most. So the budget applies to the stdout portion alone. The note sits outside it, and so does the shortfall segment, which means a bounded return runs a little past the budget by the length of what it says about itself. The number in the label and in the segment measures the content, not the string.

*cites: C22*

The label the design proposes therefore reads, for the `check` census measured above: `search: <root> (grep: check) — 70 files matched — showed N of 883 matching lines (32768-byte bound) — <exclusion note>`. The numerals are there to show the shape; every one of them is computed at run time and will drift as the repository does, and nothing in the design turns on them. On this HEAD that census is 883 matching lines across 70 files — 70 being the distinct filenames among those matching lines, which is what the file count is computed from. An earlier draft said 71, from counting distinct filenames over the whole return, in which the trailing exclusion note contributes a spurious extra one. The unit is matching lines because that is what grep emits and what `look_grep` itself splits on; converting to bytes in the label would report the budget rather than the census. The file count in front of it needs no change, since it is computed from the full stdout and stays true however little was shown — which is worth noticing, because it means even a heavily bounded return still tells the author truthfully how many files matched. And a search that fits gains no segment at all: absence means whole, the same convention by which `look --lines` annotates a range only when it had to clamp one.

*cites: C17*

One objection deserves answering here rather than later, because it is the one the label invites: this crate does not store derived values, it stores events. That rule is stated as a reason to recompute what a re-run can obtain from the shipped ledger, and for a search rooted at a directory the shown-count is not obtainable that way — the `Search` entry carries no output, and the per-file entries record what was captured rather than how much of it was handed back, keyed by filename into a map that does not preserve the order the bound consumed. That argument reaches the recursive search and stops there, and the memo should not let it stand for the verb as a whole. A grep whose root is a single file is a different instrument reached by the same words: no recursion flag is passed and no exclusions are applied, and the per-file map ends up with one key whose matched lines sit in the order grep printed them, shipped whole as that entry's output under a label naming the file. The return reconstructs from it, and the count replays out of the reconstruction. For the path label the count is recoverable too, for a different reason again: that entry's output is the whole of the selected text and `facts.jsonl` ships in the snapshot. So wherever the number can be recomputed — every file read, and every single-file search — two other things carry it. The label records what one run showed under the budget that run applied, and the budget is a judgement open to revision, so a later replay answers what today's build would show rather than what this author was shown. And the audience differs: the doctrine's case is `check` recomputing a report from a ledger it holds, whereas a label is read by someone holding the memo, whose Facts table renders labels and no captured output at all — there is nothing in front of them to recompute from. That an observation record may carry a measurement beside its bytes is not novel either; the extent already stores the captured output's length.

*cites: C19*

## ## The other `look` paths

The other `look` path turns out to have a different answer from the one its shape suggests. `look_path` computes `shown` and uses it twice, but not as one value in one place: `printed` is a string of its own that receives a *copy* of `shown` by borrow, and only afterwards is `shown` moved into the pending entry's `output`. Two independent strings exist between those two points, so a bound applied to `printed` there leaves the captured output, the label, the key, the extent, the pin and the snapshot byte-identical — the same separation `look_grep` has, in a function that reads at first glance as though it has none. There is therefore no code-shaped reason to leave the plain `look <path>` alone, and no other reason either: a whole-file read that overruns the caller's cap is the same silent cut this design exists to stop. So it is bounded too, on the same terms.

*cites: C9*

Where an asymmetry does survive is inside `look_path`, and it is about what a shortfall means rather than about whether the bound applies. Under `--lines A:B` the author named a range, and the label already records that range as delivered — clamped to the file's length, or an explicit "nothing in range" — so the shortfall it reports is one the author asked for. A bound biting on top of that is a second shortfall, chosen by tetel rather than by them, and it is recorded beside the first rather than in place of it. Under a plain `look <path>` there is no author-named range at all: the bound is the only shortfall there is, and naming it is the only thing standing between the author and a cut they would never learn about. The spelling is the grep case's, on both surfaces: the label reads `<path> — showed N of M lines (32768-byte bound)`, or `<path> lines {a}-{end} — showed N of M lines (32768-byte bound)` where a range was asked for, with M the line count of what was selected before the bound; the returned text ends with the same segment. The release rule is the grep case's too, floor included — whole lines while a whole line fits, and where none does the first line cut at a character boundary at or below the budget, which the label spells `<path> — showed 0 of M lines; first line cut mid-line at B of L bytes (32768-byte bound)`. A read that fits gains no segment in either place, and neither case is an error.

The order of the edit has to be stated for this function specifically, because the instruction given earlier — bound first, build the label from the bound — was given about `look_grep`, and `look_grep` is the function whose existing statement order already runs that way. `look_path` runs the other way. Its selection and its label are produced together by one `match` on the requested range, and all three arms of that `match` finish the label before the string the bound applies to has been created at all; the label is then handed to the pending entry untouched. An implementer who bounds the returned string where the selection is pushed into it, and leaves that `match` alone, has written a cut return with a label that says nothing about the cut — the exact defect this memo exists to remove, on the path it was added to last. So the `match` yields the base label only, and the shortfall segment is appended to it after the release rule has run over the selected text.

*cites: C20*

`look --lines` also supplies the precedent for how a shortfall should be spelled. Ask for lines 400 to 900 of a 600-line file and the label reads `lines 400-600`: it records what was delivered, not what was requested. Ask for a range wholly past the end and the label says so explicitly, on the stated principle that a bounded negative must leave a trace. Recording in the label the difference between what was asked for and what came back is therefore already how this module behaves; f3 extends it from a range the author chose to a bound tetel chose.

*cites: C10*

## ## The change, and how far it reaches

Two functions change, both in `observe.rs`. A whole-worktree census of `look_grep` finds five occurrences in two source files — the definition, one call site in `dispatch`, three doc comments — and a census of `look_path` finds four in one file: the definition, one call site in the same `dispatch`, two doc comments. No test, no binary and no other module names either of them. The bound, the marker in the returned text and the label segment are all assembled inside each function, and neither signature changes, so nothing calling them has to be touched — not `dispatch`, not the CLI, not the MCP handler.

*cites: C11*

## ## What the census refusal still guarantees

TET-28's refusal is untouched, and its wording needs no amendment. It fires on `ExtentEntry::censuses`, which reads the search's existence and its root out of an extent that is immutable once minted and that a bound on `printed` never reaches. More to the point, the refusal already tells the truth about its own scope: it "is about the search's existence and where it was rooted, never about what it found". A design that bounds what the author is shown does not make that sentence any less accurate — it was never a claim about what the author read.

*cites: C12*

Carrying that mechanism across brings its two preconditions with it. The donor states that a shortfall is not an error, and the same must hold here: hitting the bound returns a successful outcome with a bounded body, not a refusal. The code does not force that, and it is worth being exact about why, because the ordering invites the opposite reading: `printed` is assembled before any pending entry exists and the buffer is saved as the last act before the return, so an implementation that bounded while building `printed` could refuse there and discard nothing. What settles it is the crate's own rule about when to refuse. A refusal is for the case where nothing is left to tell and the remedy is singular — that is exactly how TET-28's census refusal justifies itself, against a check that stayed human-owed because only a person could tell context from conclusion — and every refusal in this crate's source is of that kind, a missing input or a forbidden flag combination, never a measurement of a result. A byte budget is not that: the number is a judgement, and an author who trips it has no act that re-runs the census smaller. Refusing would take the census away and name nothing to do instead. The donor also states that its key is the resolved path regardless of the range requested, which is what keeps two differently-sized reads of one file overlapping. That holds at the destination too: the `Search` entry is keyed by its root and each match entry by its file, both from paths alone, so a bounded search and an unbounded one of the same root overlap exactly as two unbounded ones would.

*cites: C13, C14*

## ## Whether the truncation has to be visible anywhere else

It does, in one place beyond the two the design has already settled — the label and the return itself — and the shape of that place is settled by TET-46. `check`'s standing non-coverage list gains a line. That list already distinguishes a withholding tetel chose — its own output, skipped during traversal — from things it merely suffers, like the symlinked directories and binary files the platform's grep never visits; the comment beside them insists a deliberate exclusion earns its own line rather than being folded into a sentence about platform accidents. A bound tetel applies to its own return is deliberate, so it gets its own line. That line has two halves, and only the first of them names a verb.

The first half says what f3 bounds, and it cannot be written about a census: the plain path read is inside the bound too and it is a different act — no root, no pattern, no exclusion set, and no filtering of any kind — so a line phrased around what a search returns would leave every bounded file read with no standing statement anywhere. It says instead that what `look` returned to its author is bounded. It also has to say what is not: `run` hands back the whole of a command's captured output unmeasured, on the CLI and over MCP alike, and this design does not change that. The `run` tool's own description already contemplates a command whose output is enormous and answers it by warning the author rather than by bounding anything. Naming that exclusion is what keeps the entry honest, because a standing line that named only `look` as bounded would invite a reader to take everything it did not name for whole.

The second half is not verb-scoped, and must not be, because it is true of every observation tetel records however it was taken: a fact's extent records the whole of what was observed, and nothing establishes that the author was shown all of it. That holds of a command's capture exactly as it holds of a search's or a file read's. `scope.rs` already registers it as permanently out of reach, so the entry is not an admission of a new weakness but the naming of an old one that had been invisible.

*cites: C15*

The division of labour between the two is also TET-46's, and it answers the "of what unit" question from the other end. Every string in the non-coverage list is static and none is per-search, which is why the exclusion set a particular search was given is written into that search's own label instead. The bound follows the same split, across both bounded paths: the list carries the general statement that what `look` returns to its author is bounded, and each observation's own label carries the numbers for that observation — the search record's label for a search, the path record's for a file read. Neither place needs the other's job, and neither can do it.

*cites: C16*

## ## What an author does when they hit the bound

Almost nothing new, and the honest form of that answer matters more than a paging flag would. The obvious remedies are closed for the case that motivated the ticket: a census is one search of the whole worktree for the symbol itself, so narrowing the root or trimming the pattern does not yield a smaller census, it yields something that is not a census, and `look --grep` has no other parameter to turn. What an author can do is search a subdirectory as an additional observation standing beside the census rather than replacing it, and — outside the return path entirely — reach the per-file match records, which hold every matched line and ship whole into the snapshot. So the design's claim is narrow and should be read narrowly: it does not give the author back what was withheld; it stops the withholding from being secret, on the surface they read at the time and in the memo afterwards. The bounded plain `look <path>` is the easier case: `--lines A:B` is already a first-class parameter of the same verb, so an author who wants a further whole line of the file asks for it, and each such read keys on the resolved path and therefore overlaps the first.

One residue survives even that, and it is larger than the tail past the cut, so the memo would rather name it exactly than paper it over. A line longer than the budget is never returned whole by any call, and most ranges containing it return none of it: a range only reaches that line's floored prefix if the line is the *first* one it selects. Ask for lines 12 to 20 of the longest of the four ledgers and the return is lines 12, 13 and 14 and not one byte of line 15. So exactly one range start — the line's own position — yields the prefix, every other start yields nothing of the line, and no argument to `look` reaches the remainder past the cut. Nor does the label point at the position: it reports how many of the selected lines were shown, and on a floored return the byte counts of the line it cut, but never which line overran. An author who does not already know the position finds it by narrowing the range, and while every such attempt is an ordinary `--lines` read that keys on the same resolved path and stands as its own observation, it is bisection, and the design should say so rather than imply the position is handed over. Those bytes are recoverable in full only where the grep case's are — in the fact's captured output, which for a file read is the complete selected text and ships in the snapshot beside the memo.

*cites: C18*
